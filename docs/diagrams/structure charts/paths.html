Sarx call paths

Three calls start every piece of work that Sarx does. App::new sets the app up before the window exists. resumed creates the window and the renderer. draw_frame runs once per frame, and advances the simulation and draws it. This page follows each of the three down through every crate that it reaches, with structure charts, a kind of diagram from Yourdon and Constantine’s book Structured Design. A structure chart shows which modules call which, and the values that pass between them on each call. The order of the statements inside a module stays off the chart.

The charts show the code as it will stand once every task in the Living Hand lesson is done, including the skinning in Tasks 19 and 20 and the action keys in Task 21. Some of those tasks are still to be written. A chart can therefore show a call that the code does not make yet.

Reading the charts

Each chart is drawn with a few symbols, and this section explains them one at a time. The first is the module. In Structured Design, a module is a named piece of code that a caller invokes, and that hands control back to the caller when it finishes. In Rust, a module in this sense is a function, a method or a closure. It is a different thing from a Rust module, the unit that mod declares.

Module

A plain box stands for one function or method in Sarx. The chart shows only what the function does for its caller.

A small arrow beside a call is a data couple. It stands for one value that passes on that call. The hollow circle marks where the value starts. The arrow points the way that the value travels. A couple that points down is an argument, and a couple that points up is a result.

Each chart shows one module in the middle row, the module that calls it above, and the modules that it calls below. A note under a box gives the chart that continues from it. Each box shows the function’s path in Rust syntax, such as Type::function. Each couple shows the name of its variable in the code. If a value has no variable, the chart gives it a short name of its own. The value that a method runs on, its self, is never drawn as a couple.

A few kinds of call are left off: expect, unwrap, as_mut and the other small methods on Option, struct literals and wgpu descriptors, field reads, and operators such as * on glam matrices. The From::from that each ? calls on an error is left off too. If a module calls one module twice, the chart draws the call once, and the caption says so. If a chart covers two modules that do the same job, the figure holds one drawing for each.

Path 1: setting up the app with App::new

main calls App::new once, before the event loop starts. App::new reads the hand model that the program carries inside itself, turns its poses into the simulation’s types, and builds the camera and the simulation. It touches four crates: atum, hermes, zurvan and, through the simulation, enki. Nothing on this path touches the GPU, since the window does not exist yet.

Path 2: creating the window and the renderer with resumed

Once main starts the event loop, winit calls resumed. On Windows, it calls it once, as soon as the app can draw. resumed creates the window, then sets up everything on the GPU: the connection, the surface, the hand and the ground, the buffers that feed the shaders, and the two pipelines. This path runs through atum and amaterasu. It uses the hand model that App::new read on Path 1.

Path 3: drawing a frame with draw_frame

winit calls window_event for every event on the window. A redraw request reaches draw_frame, which advances the simulation and draws the result. Each frame ends by asking for the next. This path therefore runs once per frame for as long as the program runs. A key press reaches handle_key instead, which changes the pose that the simulation aims for. This path runs through every crate apart from hermes.
