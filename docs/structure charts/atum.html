atum structure charts

This page shows how the functions in the atum crate call one another. The crate opens the window and runs the event loop. The page shows the calls with structure charts, a kind of diagram from Yourdon and Constantine’s book Structured Design. A structure chart shows which modules call which, and the values that pass between them on each call. The order of the statements inside a module stays off the chart. The crate has seven functions, and each one has a chart of its own.

Reading the charts

Each chart is drawn with a few symbols, and this section explains them one at a time. The first is the module. In Structured Design, a module is a named piece of code that a caller invokes, and that hands control back to the caller when it finishes. In Rust, a module in this sense is a function or a method. It is a different thing from a Rust module, the unit that mod declares. Below each symbol is a line from atum that the symbol stands for.

The labels on the charts follow a few conventions. Each box shows the function’s path in Rust syntax, such as Type::function. Methods and associated functions both take this form. Each couple shows the name of its variable in the code, which lets you find it in the source. Some values pass straight from one call to the next, without a variable. The chart gives such a value a short name of its own. For example, clone stands for the new Arc that Arc::clone returns. The value that a method runs on, its self, is never drawn as a couple.

The charts also simplify the code in a few places. The Window::default_attributes box stands for two calls, default_attributes and with_title. pin! is a macro, which the compiler expands into code at the place where it is used. The chart still draws it as a library module, because it behaves like a call. It takes future and gives back a pinned version of it.

A few calls are left off the charts. The first four are expect, Option::is_none, Option::as_mut and Pin::as_mut. The derived App::default is left off too. It sets both fields of an App to None. The ThreadWaker constructor is left off as well, since it only stores a value. Last, App::print_error prints the cause of an error, where there is one. That cause is a wgpu error. The chart leaves off the call to its Display::fmt.

Fan-in and fan-out

The table below counts the calls into and out of each module. Two terms describe these counts. A module’s fan-in is the number of modules that call it. Its fan-out is the number of modules that it calls. Yourdon and Constantine favour a high fan-in for a small shared helper, since one piece of code then serves many callers. They favour a moderate fan-out, because a module that calls too many others is hard to follow.

What the charts say about the design

The notes below use the charts to judge the design of the crate. Structured Design judges a design by how much each module depends on the others. It calls that dependence coupling. The couples on a chart give one measure of it. Fewer and simpler couples mean looser coupling, and looser coupling makes a better design.

Calls from winit

main hands control to EventLoop::run_app, and gets it back only when the event loop ends. From then on, winit decides when the code in atum runs. It does this by calling resumed, window_event and suspended. A structure chart usually has the program’s own code at the top, calling everything below it. An event loop turns that around. This is why a library box is at the top of Charts 2, 3 and 6. Java’s Swing works the same way. A program registers an ActionListener, and Swing calls it. The comparison stops at the thread. Swing runs its events on a thread of its own, beside main. run_app runs the event loop on the thread that called it. As a result, main stays inside run_app for the whole life of the program.

The fan-out of resumed

resumed calls eleven modules. Designers commonly keep fan-out to about seven, which puts resumed four above the limit. The two paths on Chart 2 explain the count. The first path makes nine calls, to create the window and set up the renderer. The second path makes six calls, to give the renderer a new surface. Four of those six also appear on the first path. Yourdon and Constantine call the moving of a job into a module of its own factoring. App::print_error is one result of factoring already. It moves the printing of an error and its cause out of resumed. Factoring each path of resumed into a function of its own would bring its fan-out down to two. It would also give each path a name.

Shared reporting in App::print_error

App::print_error has a fan-in of two. resumed and window_event both report a RendererError through it. Every report therefore takes the same format. The first line starts with Error:. Where the error has a cause, a second line starts with Caused by:. A change to that format happens in one place. The parameter of App::print_error is a &dyn Error. It accepts any type that implements the standard library’s Error trait. As a result, App::print_error depends on that trait alone. It works unchanged for any error type that another crate adds later.

The poll couple

Future::poll returns poll, a value of the Poll enum. Poll has two variants. Poll::Ready contains the future’s output. Poll::Pending contains no data. A Java method in this position would often return the output, or null where there is none yet. Yourdon and Constantine call a value that doubles as a signal in that way a hybrid couple. A chart can draw a hybrid couple only as plain data. A Rust enum instead gives each case its own variant. The compiler then rejects a match that leaves a variant out. A sealed interface in Java comes closest, since a switch over one must cover every case too.

The transaction centre in window_event

A transaction centre is Yourdon and Constantine’s name for a module that looks at the kind of its input. It then passes the input to one of several actions. The match over WindowEvent makes window_event a transaction centre. This is why every call beneath it on Chart 3 has a diamond. WindowEvent has many variants. The other arm takes every variant that the arms above it leave. As a result, the match covers every variant, as the compiler requires.

Arc on Charts 2 and 4

Arc::new in resumed puts the window behind an Arc. An Arc is a pointer that counts how many owners share the value behind it. Arc::clone adds an owner, and returns a second pointer to the same window. resumed passes that second pointer to Renderer::new, which hands it to wgpu to create the surface. On every later call, Arc::clone gives Renderer::resume another Arc in the same way. The window therefore stays alive while either the App or the surface still owns an Arc to it. A Java reference works like the counting half of an Arc. The garbage collector keeps an object alive while anything refers to it. The comparison stops at freeing. Java frees an object at some later collection. An Arc frees its value at the moment that the last owner drops it. On Chart 4, Waker::from takes the ThreadWaker inside an Arc for the same reason. A future can keep clones of the waker after poll returns, and each clone is one more owner.

pin! on Chart 4

pin! pins the future. A pinned value stays at one address in memory until it is dropped. A future that an async fn creates can store a reference into itself across an .await. Moving that future would leave the reference pointing at the old address. Future::poll therefore takes the future as a Pin<&mut Self>. A Pin is a pointer that promises that the value behind it stays where it is. The compiler rejects a call to poll on a future that could still move. Java has no counterpart to pinning. Its garbage collector moves objects freely, and updates every reference to them as it does.
