Boxes take Rust’s path syntax, Type::function, for methods and associated functions alike. Couples take the name of the variable in the code, letting you find each one in the source. Where the code passes a value straight on without storing it in a variable, the couple takes a short name for it, such as clone for the second Arc that Arc::clone returns. The value that a method runs on, its self, is left off the couples.

The Window::default_attributes box stands for default_attributes and with_title together. pin! is a macro, which the compiler expands into code where it is used. The chart draws it as a library module all the same, since it does a call’s job. Calls to expect, Option::is_none, Option::as_mut and Pin::as_mut are left out. So are the derived App::default, which sets both fields of an App to None, and the ThreadWaker constructor, which only stores a value. The cause that resumed prints is a wgpu error, and the call to its Display::fmt is left out too.

Fan-in and fan-out

Fan-in is the number of modules that call a module. Fan-out is the number of modules that it calls. Yourdon and Constantine want high fan-in for small shared helpers, since one piece of code then serves many callers. They also want moderate fan-out, because a module that calls too many others is hard to follow. resumed calls ten modules, three above the usual rule of thumb of about seven.

What the charts say about the design

Structured Design judges a design by two measures. Coupling is how much one module depends on another, and the couples on a chart are its visible part: fewer and simpler couples mean looser coupling. Cohesion is how closely the statements inside one module serve a single job. A chart shows coupling directly, and these notes read the charts that way.

Calls from winit

main hands control to EventLoop::run_app and gets it back once the event loop ends. From then on, winit decides when Sarx’s code runs, by calling resumed and window_event. A structure chart usually has the program’s own code at the top, calling everything below it. The event loop turns that around, which is why a library box sits at the top of Charts 2 and 3. Java’s Swing works the same way: a program registers an ActionListener, and Swing calls it. The comparison stops at the thread. Swing runs its events on a thread of its own beside main. run_app runs the event loop on the thread that called it, meaning main stays inside run_app for the life of the program.

The fan-out of resumed

resumed calls ten modules, which fall into three jobs. Four calls create the window: Window::default_attributes, ActiveEventLoop::create_window, Arc::new and Window::inner_size. Three set up the renderer: Arc::clone, Renderer::new and block_on. The last three report a failure: Display::fmt, Error::source and ActiveEventLoop::exit. Yourdon and Constantine call moving one job into a module of its own factoring. Factoring the failure report into its own function would bring the fan-out of resumed down to eight, and give the report a name.

The poll couple

Future::poll returns poll, a Poll enum with two variants. Poll::Ready carries the future’s output, and Poll::Pending carries no data. A Java method in this position would often return either the output or null. Yourdon and Constantine call a value that doubles as a signal in that way a hybrid couple, and a chart can only draw it as plain data. A Rust enum gives each case its own variant, and the compiler rejects a match that leaves one out. A sealed interface in Java comes closest, since a switch over one must cover every case too.

The transaction centre in window_event

A transaction centre is Yourdon and Constantine’s name for a module that looks at the kind of its input and passes it to one of several actions. The match over WindowEvent in window_event is one, which is why every call beneath it on Chart 3 has a diamond. WindowEvent has many variants, and the other arm takes every variant that the arms above it leave. The match therefore covers them all, as the compiler requires.

Arc on Charts 2 and 4

Arc::new in resumed puts the window behind an Arc, a pointer that counts how many owners share the value. Arc::clone adds an owner and returns a second pointer to the same window, which Renderer::new passes on to the surface. The window then stays alive while either the App or the surface holds a pointer to it. Every Java reference behaves like this shared part, since the garbage collector keeps an object alive while anything refers to it. The comparison stops at freeing. Java frees an object at some later collection, whereas an Arc frees its value at the moment that the last owner drops it. On Chart 4, Waker::from takes the ThreadWaker inside an Arc for the same reason: a future can keep clones of the waker after poll returns, and each clone is one more owner.

pin! on Chart 4

pin! pins the future, meaning the future stays at one address in memory until it is dropped. A future that an async fn creates can store a reference into itself across an .await, and moving the future would leave that reference pointing at the old address. Future::poll therefore takes the future as a Pin<&mut Self>, a pointer that promises the value behind it stays put, and the compiler rejects a call to poll on a future that could still move. Java has no counterpart, as its garbage collector moves objects freely and updates every reference to them.
