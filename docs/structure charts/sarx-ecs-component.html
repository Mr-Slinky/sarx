Component structure charts

This page shows how the functions in component.rs call one another. The file defines ComponentVec, one column in an archetype table, and ComponentInfo, which describes the component type in that column. The page does this with structure charts, a kind of diagram from Yourdon and Constantine’s book Structured Design. A structure chart shows which modules call which. It also shows the values that pass between them on each call. The file has eleven functions and methods, and one closure. Ten charts cover them.

Reading the charts

Each chart is drawn with a few symbols, and this section explains them one at a time. The first is the module. In Structured Design, a module is a named piece of code that a caller invokes, and that hands control back to the caller when it finishes. In Rust, a module in this sense is a function, a method or a closure. It is a different thing from a Rust module, the unit that mod declares. Below each symbol is a line from component.rs that the symbol stands for.

A plain box stands for one function, method or closure in component.rs.

An arrow runs from a module to a module that it calls. The caller is always drawn above.

Data couple

A small arrow beside a call is a data couple. It stands for one value that passes on that call. The hollow circle marks where the value starts, and the arrow points the way that the value travels. A couple that points down is an argument, and a couple that points up is a result.

let end = self.ptr_at(self.len);
// len goes down as an argument, and end comes up as the result
Conditional call

A diamond where the arrow leaves the caller marks a call that happens only when a test passes.

if self.len == self.capacity {
    self.grow();
}
Repeated calls

A curved arrow marks a loop. It crosses every call that runs once on each pass of the loop.

Library module

A box with a second line inside each side is a function that the standard library defines.

Code outside the file

A dashed box stands for code outside component.rs. It shows where the first call on a chart comes from.

let mut source = ComponentVec::new(info);   // in the module documentation

The labels on the charts follow a few conventions. Each box shows the function’s path in Rust syntax, such as Type::function. A method on a raw pointer appears as pointer::method. Each couple shows the name of its variable in the code. Some values pass straight from one call to the next, without a variable, and the chart gives such a value a short name of its own. For example, address stands for the pointer that ptr::without_provenance_mut returns. The value that a method runs on, its self, is never drawn as a couple.

A caller sometimes calls one module from two places. The chart draws a box for each call where the two calls pass different values, or where only one of them has a diamond. array_layout on Chart 6 is one example.

A few calls are left off the charts. The first two are Option::expect and Result::expect, which panic on a failure. The couple above them therefore shows the unwrapped value. The Some that wraps drop_value is left off too. So are three macros: assert_ne!, debug_assert! and debug_assert_eq!. Arguments to a macro still appear, where they make a call.

What the charts say about the design

The notes below use the charts to judge the design of the file. Structured Design judges a design by how much each module depends on the others, which it calls coupling.

A type that survives through drop_value

ComponentVec forgets its component type, yet Chart 9 still runs the clean-up code of that type. Chart 2 makes this possible. The compiler generates one copy of drop_value for each T, and ComponentInfo::of stores the address of the matching copy. Each copy accepts a *mut u8, meaning every copy fits the same field type. A Java programmer would pass a Consumer<Object> for the same job. The comparison stops at generics. Java erases a type parameter and shares one method body, whereas Rust generates a separate body for each type.

One address calculation in ptr_at

ComponentVec::ptr_at has a fan-in of four, the highest among the functions in the file. Fan-in counts the modules that call a module. Every path to a component passes through this one multiplication, which gives the rule "index times size" one home.

Matching layouts through array_layout

The allocator requires alloc::realloc and alloc::dealloc to receive the layout that the block was allocated with. The vector stores no layout for its block. array_layout rebuilds one from the capacity each time, on Charts 6 and 9. Its fan-in of two therefore enforces a rule of the allocator. The two callers stay in agreement for as long as capacity matches the block, and only ComponentVec::grow changes capacity after creation.

The fan-out of grow

ComponentVec::grow calls seven different modules, and designers commonly keep fan-out to about seven. It reaches that limit. Six of the seven are library calls, and parts 2 and 3 of Chart 6 add three of the seven.

The call from move_component to push

Chart 8 reuses ComponentVec::push for the copy onto target. A move therefore inherits the growth rule of Chart 5, along with its pointer rule. A pointer into target from before the move stops being valid when the move grows that block. Pointers into self keep their address, although the component at index has changed.
