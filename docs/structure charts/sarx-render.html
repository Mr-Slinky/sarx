sarx-render structure charts

This page shows how the functions in the sarx-render crate call one another. The crate draws each frame on the GPU, through the wgpu library. The page does this with structure charts, a kind of diagram from Yourdon and Constantine’s book Structured Design. A structure chart shows which modules call which. It also shows the values that pass between them on each call. The order of the statements inside a module stays off the chart. The crate has twenty-seven functions and methods, and one closure, in Mesh::to_bytes. Ten charts cover them. Most charts cover one job that another crate asks the renderer to do, such as drawing a frame. Each of the others covers one step that is too large to fit on the chart of its job.

Reading the charts

Each chart is drawn with a few symbols, and this section explains them one at a time. The first is the module. In Structured Design, a module is a named piece of code that a caller invokes, and that hands control back to the caller when it finishes. In Rust, a module in this sense is a function, a method or a closure. It is a different thing from a Rust module, the unit that mod declares. Below each symbol is a line from sarx-render that the symbol stands for.

Module

A plain box stands for one function or method in sarx-render. The chart shows only what the function does for its caller.

fn reconfigure(&self) {
Call

An arrow runs from a module to a module that it calls. The caller is always drawn above.

self.gpu.resize(width, height);   // in Renderer::resize
Hidden call

A dashed arrow is a call that never appears in the code. Sometimes a library makes the call. At other times, the compiler adds the call in place of an operator, such as ?.

let surface = instance.create_surface(Arc::clone(&window))?;
// on an error, ? calls From::from
Data couple

A small arrow beside a call is a data couple. It stands for one value that passes on that call. The hollow circle marks where the value starts. The arrow points the way that the value travels. A couple that points down is an argument, and a couple that points up is a result.

let gpu = GpuContext::new(window, width, height).await?;
// window, width and height go down as arguments, and gpu comes up as the result
Conditional call

A diamond where the arrow leaves the caller marks a call that happens only when a test passes.

if suboptimal {
    self.gpu.reconfigure();
}
Repeated calls

A curved arrow marks a loop. It crosses every call that runs once on each pass of the loop.

.flat_map(|coordinate| coordinate.to_ne_bytes())
// collect calls the closure once per coordinate
Library module

A box with a second line inside each side is a library module. It is a function that wgpu or the standard library defines, and that sarx-render calls.

queue.submit([encoder.finish()]);
Module in another crate

A dashed box is a function in another Sarx crate. It shows where the first call on a chart comes from. The sarx-app page has a chart for it.

&& let Err(error) = renderer.render()   // in window_event, sarx-app

The labels on the charts follow a few conventions. Each box shows the function’s path in Rust syntax, such as Type::function. Methods and associated functions both take this form. Each couple shows the name of its variable in the code, which lets you find it in the source. Some values pass straight from one call to the next, without a variable. The chart gives such a value a short name of its own. For example, limits stands for the value that Limits::default returns. The value that a method runs on, its self, is never drawn as a couple. render and reconfigure, for example, read the surface, the device and the configuration from self. Their call arrows therefore appear without couples.

The charts also simplify the code in a few places. The Clone::clone box stands for the clone method of whatever window type the caller passes. sarx-app passes an Arc<Window>, and for that type the method is Arc::clone.

A few calls are left off the charts. The first two are Default::default and TextureViewDescriptor::default. The struct literals that build each descriptor are left off too. So are the Ok and Some that wrap a result, and the Option::as_mut that reaches a SurfaceContext. Two macros are left off as well. include_str! copies the shader into the program while it compiles. vec! builds the triangle’s list of vertices.

One more kind of call is left off. A ? calls From::from on every error that it passes back, even one that is already a RendererError. In that case, From::from converts the error into itself. These calls come from Renderer::new, GpuContext::recreate and GpuContext::resume. Two more come from the calls to Option::ok_or.

Rust also drops values without a call in the code. Assigning a new value to a field, for example, drops the value that was there. The charts leave these drops off. They draw only the two drop calls that the code writes out. The first ends the render pass on Chart 6. The second frees the old surface on Chart 9.

Last, a caller sometimes calls one module from two places. Renderer::render does this with GpuContext::reconfigure. The chart then draws the module once, under that caller.

Fan-in and fan-out

The table below counts the calls into and out of each module. Two terms describe these counts. A module’s fan-in is the number of modules that call it. Its fan-out is the number of modules that it calls. Yourdon and Constantine favour a high fan-in for a small shared helper, since one piece of code then serves many callers. They favour a moderate fan-out, because a module that calls too many others is hard to follow. Three rows of the table stand out. GpuContext::new calls eighteen modules, across Charts 2 and 3. Renderer::render calls fourteen. GpuContext::create_surface_context calls eight. It is also one of five modules with a fan-in of two.

What the charts say about the design

The notes below use the charts to judge the design of the crate. Structured Design judges a design by how much each module depends on the others. It calls that dependence coupling. The couples on a chart give one measure of it. Fewer and simpler couples mean looser coupling, and looser coupling makes a better design.

Tramp data through Renderer

Renderer::new passes window, width and height to GpuContext::new without reading them. Renderer::resize and Renderer::resume do the same with their arguments. Renderer::suspend takes no arguments, and only passes the call on. Yourdon and Constantine call data that a module only passes on tramp data. They usually count it against a design. Here it is a decision, taken to keep GpuContext private to sarx-render, together with the wgpu types inside it. Renderer and RendererError are the only public items in the crate. As a result, a change to the fields or methods of GpuContext affects no other crate.

The fan-out of GpuContext::new

GpuContext::new calls eighteen modules, across Charts 2 and 3. A common rule of thumb keeps fan-out to about seven, and eighteen is more than twice that. The couples on Chart 2 show why the calls come in a fixed order. Each wgpu call takes a value that an earlier call returned. instance creates surface. surface helps choose adapter, and adapter opens device. The comments in the code divide the body into six steps. They are creating the instance and the surface, choosing the adapter, opening the device, choosing the configuration, checking anti-aliasing, and building the SurfaceContext. Yourdon and Constantine call the moving of a job into a module of its own factoring. Factoring each step into a function of its own would bring the fan-out down to six. The couples of each new function would then state what its step needs and returns. create_surface_context on Chart 10 already performs the surface steps, for every later surface. GpuContext::new cannot call it for the first surface, however. create_surface_context checks the surface against self.format, and GpuContext::new reads that format from the first surface’s configuration.

The stages of Renderer::render

Renderer::render calls fourteen modules. Most of them fall into four stages. First, it gets a texture with Surface::get_current_texture and Texture::create_view. Second, it starts recording with Device::create_command_encoder and CommandEncoder::begin_render_pass. Third, it records the draw with RenderPass::set_pipeline, Buffer::slice, RenderPass::set_vertex_buffer and RenderPass::draw. It then ends the pass with drop, and the recording with CommandEncoder::finish. Fourth, it hands the work to the GPU with Queue::submit and Queue::present. Yourdon and Constantine also describe a kind of module that explains the remaining calls. A transaction centre looks at the kind of its input, then passes the input to one of several actions. Renderer::render is one. Its input is the value that Surface::get_current_texture returns. The arms of the match on that value decide between drawing, reconfiguring, recreating and returning at once.

Shared modules

Five modules have a fan-in of two. Four of them are SurfaceContext::new, SurfaceContext::reconfigure, GpuContext::create_msaa_view and GpuContext::create_surface_context. The fifth is the From::from that turns a CreateSurfaceError into a RendererError. Each of the five does a job that two callers need. SurfaceContext::new, for example, builds a SurfaceContext at start-up, and again for every later surface. Yourdon and Constantine count fan-in like this in a design’s favour, since a change to the job happens in one place.

Ending the render pass

CommandEncoder::begin_render_pass returns a RenderPass<'encoder>. The 'encoder is a lifetime. It tells the compiler that render_pass borrows encoder for as long as the pass exists. The borrow is mutable. While it lasts, no other code can use encoder. CommandEncoder::finish takes encoder by value. The compiler refuses to give away a value that is still borrowed. render therefore passes render_pass to drop first. Dropping the pass ends the borrow. The hidden call to its Drop::drop also ends the pass inside wgpu. Java has no counterpart. A Java object stays usable while anything refers to it, and nothing checks the order of such calls at compile time.

Errors through ?

The From::from calls on Charts 3 and 10 never appear in the code. The ? after a call makes the function return early on an error. On the way out, it converts the error to the function’s own error type, through From. The nearest Java pattern catches an exception, wraps it, and throws the wrapper: catch (IOException e) { throw new RendererException(e); }. The two differ in how the conversion happens. Rust picks the From implementation at compile time, from the type of the error. The error then travels back as an ordinary return value, with no stack unwinding.

Box, Arc and dyn on Charts 2 and 8

Box::new moves the cloned window onto the heap. It returns a Box, the pointer that owns the window. InstanceDescriptor::new_with_display_handle takes a Box because it stores the display as a trait object. A trait object is a value known only by the traits that it implements. The compiler cannot know its size in advance, which is why it has to be reached through a pointer. An Arc is a pointer that several owners can share at once. Each Arc::clone adds one owner, and returns a new pointer to the same value. The value is freed when the last owner drops its pointer. The window that reaches GpuContext::new is already an Arc<Window>, from sarx-app. Arc::new wraps it in a second, outer Arc. GpuContext::resume on Chart 8 wraps the window in the same way. The surface receives a clone of the outer Arc. SurfaceContext keeps the outer Arc itself, as an Arc<dyn DisplayAndWindowHandle>. That type is another trait object. It lets SurfaceContext keep a window of any type, without a type parameter of its own. A Java field of an interface type works the same way. The two differ in the pointer. Every Java object is already reached through a reference. Rust asks for the Box or the Arc to be written out.

Lazy iterators on Chart 5

slice::iter, Iterator::flatten and Iterator::flat_map each return at once, before they read a single coordinate. slice::iter returns an iterator over the vertices. flatten and flat_map each return an iterator that wraps the one before it. Iterator::collect does all of the work. It pulls one value at a time through the chain, and calls the closure for each coordinate. A Java Stream behaves the same way. map and flatMap describe the work, and a terminal operation such as collect runs it. The two differ in the code that actually runs. A Java stream builds an object for each stage, and calls through each one in turn. The Rust compiler can inline the whole chain into one plain loop, in a release build.
