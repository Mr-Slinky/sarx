sarx-render structure charts

A structure chart, from Yourdon and Constantine’s Structured Design, shows which modules call which, and what passes between them on each call. It leaves out the order of statements inside a module. These five charts cover the eleven functions and methods in the sarx-render crate, which draws each frame on the GPU through wgpu, with one chart for each job that the rest of Sarx asks the crate to do.

Reading the charts

In Structured Design a module is a named piece of code that a caller can invoke and get control back from. In Rust that is a function or a method. Each symbol below comes with the line in sarx-render that produces it.

Module

One function or method in sarx-render. The chart shows what it does for its caller, not the statements inside it.

fn reconfigure(&self) {
Call

An arrow from a module down to a module that it calls. The caller is drawn above.

self.gpu.resize(width, height);   // in Renderer::resize
Hidden call

A dashed arrow is a call that Sarx’s code never writes out. A library makes it, or the compiler adds it in place of an operator such as ?.

let surface = instance.create_surface(window)?;
// on an error, ? calls From::from
Data couple

A value passed on a call. The hollow circle marks the tail, and the arrow points the way the value travels: down into the called module, or up as its result.

let gpu = GpuContext::new(window, width, height).await?;
// window, width and height go down, gpu comes back up
Conditional call

The diamond means the call happens only when a test passes.

if suboptimal {
    self.gpu.reconfigure();
}
Library module

A function from wgpu or the standard library that sarx-render calls but does not define.

queue.submit([encoder.finish()]);
Module in another crate

A dashed box is a function in another Sarx crate, drawn to show where each chart starts. The sarx-app page charts it in full.

renderer.render();   // in window_event, sarx-app

Boxes take Rust’s path syntax, Type::function, for methods and associated functions alike. Couples take the name of the variable in the code, letting you find each one in the source. Where the code passes a value straight on without storing it in a variable, the couple takes a short name for it, such as limits for the value that Limits::downlevel_defaults returns. The value that a method runs on, its self, is left off the couples. render and reconfigure, for example, read the surface, device and configuration from self, and their calls therefore show no couples.

The Clone::clone box stands for the clone of whatever window type the caller passes. For sarx-app’s Arc<Window>, that is Arc::clone. Calls to Default::default and TextureViewDescriptor::default are left out, as are the struct literals that build each descriptor and the Ok(Self { gpu }) that ends Renderer::new. The ? in Renderer::new also calls From::from, converting a RendererError into a RendererError, and that call is left out too.

Fan-in and fan-out

Fan-in is the number of modules that call a module. Fan-out is the number of modules that it calls. Yourdon and Constantine want high fan-in for small shared helpers, since one piece of code then serves many callers. They also want moderate fan-out, because a module that calls too many others is hard to follow. GpuContext::new calls fourteen modules across Charts 1 and 2, twice the usual rule of thumb of about seven. Renderer::render calls nine.

What the charts say about the design

Structured Design judges a design by two measures. Coupling is how much one module depends on another, and the couples on a chart are its visible part: fewer and simpler couples mean looser coupling. Cohesion is how closely the statements inside one module serve a single job. A chart shows coupling directly, and these notes read the charts that way.

Tramp data through Renderer

Renderer::new passes window, width and height to GpuContext::new without reading them, and Renderer::resize does the same with the size. Yourdon and Constantine call data that a module only passes on tramp data, and usually count it against a design. Here it is a decision, taken to keep GpuContext and the wgpu types inside it private to sarx-render. Renderer and RendererError are the crate’s whole public surface, and GpuContext can change shape without any other crate noticing.

The fan-out of GpuContext::new

GpuContext::new calls fourteen modules. The couples on Chart 1 show why their order is fixed: each wgpu call takes a value that an earlier call returned. instance creates surface, surface helps choose adapter, and adapter opens device. The comments in the code already divide the body into four steps: creating the instance and surface, choosing the adapter, opening the device, and configuring the surface. Factoring each step into a function of its own would bring the fan-out down to four, with each function’s couples stating what that step needs and returns.

The stages of Renderer::render

Renderer::render calls nine modules in three stages. It gets a frame with Surface::get_current_texture and Texture::create_view. It records commands with Device::create_command_encoder, CommandEncoder::begin_render_pass, drop and CommandEncoder::finish. It then hands the work over with Queue::submit and Queue::present. The match on frame or status is a transaction centre, Yourdon and Constantine’s name for a module that passes its input to one of several actions by kind. Its arms decide between drawing, reconfiguring, and returning at once.

Ending the render pass

CommandEncoder::begin_render_pass returns a RenderPass<'encoder>. The 'encoder is a lifetime: it tells the compiler that render_pass borrows encoder, mutably, for as long as the pass exists. CommandEncoder::finish takes encoder by value, and the compiler refuses to give away a value that is still borrowed. render therefore passes render_pass to drop first. Dropping it ends the borrow, and the hidden call to its Drop::drop ends the pass inside wgpu. Java has no counterpart: an object there stays usable while anything refers to it, and nothing checks the order at compile time.

Errors through ?

The three From::from calls on Chart 2 never appear in the code. The ? after a call returns early on an error, converting the error to the function’s own error type through From on the way out. The nearest Java pattern catches an exception, wraps it, and throws the wrapper: catch (IOException e) { throw new RendererException(e); }. The comparison stops at the mechanism. Rust picks the From implementation at compile time from the error’s type, and the error travels back as an ordinary return value, with no stack unwinding.

Box and Arc on Chart 1

Box::new moves the cloned window onto the heap and returns a Box, the pointer that owns it. InstanceDescriptor::new_with_display_handle takes a Box because it stores the display as a trait object, a value known only by the traits that it implements, whose size the compiler cannot know in advance. A Java interface reference works the same way, since every Java object lives on the heap. The Clone::clone before it is an Arc::clone for sarx-app’s window, meaning the descriptor gets one more owner of the same window rather than a second window.
